## 1. One-line pitch

An RL agent that learns **which security alert a human analyst should investigate next**, trained first on a hand-written reward and then re-trained on a reward model learned from **real human preference judgments (RLHF)**.

---

## 2. The real problem

A Security Operations Centre (SOC) receives thousands of alerts per day. A small team can investigate a tiny fraction of them. The overwhelming majority are false positives; a handful are real intrusions. Every hour a real intrusion sits un-triaged in the queue is another hour of attacker dwell time.

The industry's default answer is **sort by the severity label the detection vendor assigned**. That label is generated by a product that has never seen your business, does not know which of your servers matter, and does not know how many analyst-minutes are left in the shift.

So the operational question is genuinely sequential and genuinely hard:

> Given a growing queue, a fixed analyst time budget, and uncertainty about which alerts are real — what order do you work them in?

That is an MDP. Nobody has a closed-form answer to it. "Alert fatigue" is a standard industry term precisely because this problem is unsolved in practice.

### Why this problem and not another

- It is a **true sequential decision problem** (each action consumes the budget and changes the queue), not a bandit or a classification task dressed up as RL.
- The reward is **genuinely un-writable by hand** — how many wasted analyst-minutes equal one three-hour detection delay? There is no correct number. This makes RLHF *necessary* rather than bolted on, which matters because RLHF is 7 lectures of this syllabus.
- It maps to both team members' actual backgrounds (see §9).

## 3. The MDP

This is the part both team members must be able to draw on a whiteboard from memory.

### 3.1 Episode

One **8-hour analyst shift** = 480 simulated minutes. Alerts arrive continuously. The agent repeatedly chooses an action; each action consumes simulated minutes; the episode ends when the clock runs out.

### 3.2 State — discretised (for tabular methods)

| Feature | Buckets | Values |
|---|---|---|
| `max_severity_in_queue` | 4 | 0=info, 1=low, 2=medium, 3=high |
| `queue_len_bucket` | 4 | `[0,10)`, `[10,40)`, `[40,100)`, `[100,∞)` |
| `oldest_age_bucket` | 4 | `[0,30)`, `[30,90)`, `[90,180)`, `[180,∞)` minutes |
| `time_left_bucket` | 3 | `>240`, `[60,240]`, `<60` minutes |
| `max_asset_crit_in_queue` | 3 | 0=dev box, 1=standard, 2=crown jewel |

**|S| = 4 × 4 × 4 × 3 × 3 = 576 states.** With 5 actions that is a 576×5 Q-table — 2,880 numbers. It fits on a screen. You can print the learned policy and read it.

### 3.3 State — continuous (for DQN, Phase 3)

Same underlying situation, no bucketing. ~20 floats: queue length, mean/max severity, mean/max age, mean/max asset criticality, mean verify cost, fraction of queue by alert type (6 types), normalised time remaining, alerts handled so far, true incidents confirmed so far.

**Why both:** the discretised version proves you understand tabular RL and gives an interpretable policy; the continuous version is the honest motivation for function approximation (CO3 — "explain the need for function approximation"). Showing DQN beating tabular *on the richer state* is the deliverable, not just "we also did DQN".

### 3.4 Actions — 5, fixed

The agent does **not** pick an alert out of the queue. It picks **which triage rule to apply right now**:

| # | Action | Effect |
|---|---|---|
| 0 | `PULL_HIGHEST_SEVERITY` | Investigate the highest-severity alert |
| 1 | `PULL_OLDEST` | Investigate the longest-waiting alert |
| 2 | `PULL_MOST_CRITICAL_ASSET` | Investigate the alert on the most business-critical asset |
| 3 | `PULL_CHEAPEST` | Investigate the fastest-to-verify alert (clear backlog) |
| 4 | `BULK_CLOSE_LOW_RISK` | Auto-close up to 10 low-severity, low-criticality alerts (costs 2 min) |

**This is the single most important design decision in the project.** Defend it like this:

> A naive formulation makes the action "pick one of N alerts", where N changes every step and can be in the hundreds. That gives a variable-sized action space, which breaks tabular Q-learning outright and makes DQN awkward. By making the action *a choice of triage policy* rather than *a choice of alert*, the action space stays fixed at 5 regardless of queue size, the Q-table stays small, and — critically — the learned policy is human-readable. A security manager can look at the table and say "I agree" or "I don't". That interpretability is worth more in this domain than the extra expressiveness we gave up.

Ties are broken **deterministically by alert ID** so runs are reproducible. Empty queue → clock advances 5 minutes, reward 0.

### 3.5 Reward — v1, hand-written

| Event | Reward |
|---|---|
| Investigate a **true incident** | `+100 × exp(−delay/120) × asset_multiplier` |
| Investigate a **false positive** | `−1 × verify_cost_min` (i.e. −5 to −40) |
| Bulk-close a false positive | `+0.5` each (queue hygiene) |
| Bulk-close a **true incident** | `−150 × asset_multiplier` |
| End of shift: true incident never triaged past its deadline | `−200 × asset_multiplier` |

`asset_multiplier` = 1.0 / 1.5 / 2.5 for criticality 0 / 1 / 2. `delay` = minutes between the alert arriving and being investigated.

**Every one of these numbers is made up.** Say that out loud in the viva — it is the entire motivation for Phase 4. We are currently optimising *our arbitrary opinion* about the trade-off between wasted time and missed breaches. Phase 4 replaces it with a trade-off learned from humans.

Note the deliberate trap in action 4: bulk-close shrinks the queue fast and earns small positive rewards. If the agent learns to spam it, that is **reward hacking**, and catching it is a named deliverable (§7).

## 4. The environment (simulator)

There is no public dataset of "analyst triage decisions", so we simulate — and we document that as our primary external-validity limitation rather than hiding it.

### 4.1 Alert generation

Alerts arrive as a **Poisson process**, λ ≈ 0.35/minute → ~170 alerts per 480-minute shift. An analyst can realistically complete ~35. That ~20% coverage ratio is the whole point.

Each alert carries:

```
id, arrival_time, severity (0-3), asset_criticality (0-2),
verify_cost_min (5/10/20/40), alert_type (6 types),
is_true_incident (HIDDEN from agent), deadline_min (dwell-time budget)
```

### 4.2 The key modelling assumption

`P(true incident)` ≈ **3% base rate**, modulated by alert type, asset criticality, and time of day. Crucially, **severity is only weakly correlated with truth** (target Pearson r ≈ 0.3–0.4), while the *combination* of type + asset criticality + verify cost is substantially more informative.

This is the assumption that makes a learned policy able to beat severity-sort. It is grounded in the widely-reported industry reality that vendor severity labels are poor predictors — but it **is an assumption we are building in**, and `EXPLAIN.md` and the final report must both say so plainly. If we made severity a perfect predictor, severity-sort would be optimal and there would be no project.

Feature distributions should be sanity-checked against a public IDS dataset (CICIDS2017 or UNSW-NB15) so the numbers aren't invented from nothing. This is a "nice-to-have" for the report, not a blocker.

### Note on the DP phase (be honest about this)

The true transition dynamics of the queue are not analytically available, so we do **model-based** DP: run 50k episodes under a random policy, count transitions to build estimates `P̂` and `R̂`, then run value iteration on the estimate.

The resulting policy is optimal **for the estimated model**, not for the true environment. Say exactly that. It is still a useful reference ceiling and it demonstrates real DP understanding. Additionally, hand-work one tiny 5-state MRP on paper for the report to show the Bellman equations explicitly.

## 6. RLHF design (Phase 5)

### 6.1 Why

The reward numbers in §3.5 are invented. Humans cannot reliably assign such numbers, but they *are* good at comparing two outcomes. So we ask for comparisons instead of numbers.

### 6.2 Data collection

A small web page replays two shifts **side by side** — same alert stream, two different policies. Each side shows a compact timeline of actions plus outcome cards (incidents caught and when, incidents missed, minutes wasted). The labeller clicks **left / right / can't tell**.

- Target: **300 labelled pairs**.
- Labellers: Pranav, Diya, 3–4 classmates, and — if obtainable — one working analyst via Diya's KPMG team. Practitioner labels, even a handful, materially raise the credibility of the whole project.
- **50 pairs must be labelled by both Pranav and Diya** to compute inter-annotator agreement (Cohen's κ). Report it. If κ is low, that is itself a finding about how ill-defined "good triage" is.

Time cost: ~300 × 20 s ≈ 100 minutes of human effort total.

### 6.3 Reward model

Standard trajectory-comparison formulation (Christiano et al., 2017), which is also exactly what the syllabus describes in Lectures 30–32:

```
P(τ_A ≻ τ_B) = exp(Σ r̂(s,a) over τ_A) / (exp(Σ_A) + exp(Σ_B))
```

Loss = binary cross-entropy against the human label. `r̂` is a small MLP over state features + one-hot action. Roughly 40 lines of PyTorch. This is the **Bradley–Terry model**, and you should be able to write that loss on a whiteboard.

Hold out 20% of pairs. Report train vs held-out accuracy.

### 6.4 Then

Re-train the Phase 2/3 agents using `r̂` in place of the hand-written reward. Evaluate:

1. **Held-out preference agreement** — do humans prefer the RLHF policy over the hand-reward policy on fresh, never-labelled pairs? This is the headline graph.
2. **Ground-truth metrics** — how do the two policies compare on incidents-missed and MTTD? If the RLHF policy is *worse* on ground truth but *preferred* by humans, that is a genuinely interesting result and must be reported, not buried.

## 7. The reward-hacking audit (a named deliverable, not an afterthought)

Once the agent optimises a *learned* reward, it can find loopholes that score well and behave badly. We go hunting deliberately. Four specific experiments:

1. **Bulk-close exploit.** Track action-4 frequency across training. Does `r̂` assign positive value to bulk-close in states where ground truth says it is harmful?
2. **Reward-model overfitting.** Train vs held-out pair accuracy. A large gap means we are optimising noise.
3. **Out-of-distribution drift.** Measure state-visitation overlap between the RLHF policy and the policies that generated the labelled pairs. If the new policy spends time in regions the reward model never saw labels for, its reward estimates there are unfounded — a real and explainable failure mode.
4. **Label quality.** Cohen's κ between the two annotators (§6.2).

Whatever we find gets written up — including if we find nothing. "We looked for X with method Y and did not find it" is a valid, reportable result.

> Pranav, this is deliberately the ChurnLens move a second time. On ChurnLens you audited your own pipeline, found test-set leakage, and retracted a better-looking ₹3.8L for the honest ₹4.2L. Doing that once can look like luck. Doing it twice, in a different domain, is a pattern — and it is the single most valuable thing on either of your resumes for a research or ML-engineering interview.

## 8. Evaluation

### Baselines (all must be implemented)

| Baseline | Why it's there |
|---|---|
| Random | Floor |
| FIFO | The naive human default |
| **Severity-sort** | **What the industry actually does — this is the one to beat** |
| Cheapest-first | Throughput-maximising strawman |
| DP-on-estimated-model | Reference from Phase 1 |
| **Oracle-greedy** (sees hidden labels) | Upper bound — nothing can beat this |

### Metrics

- **MTTD** — mean time to detect, over true incidents that were caught
- **Recall@deadline** — % of true incidents caught before their dwell deadline
- **Wasted minutes** — analyst time spent on false positives
- **Critical misses** — count of `asset_criticality = 2` incidents missed
- **Composite cost** (₹) — under a clearly stated cost assumption

### Protocol (non-negotiable)

- **5 random seeds**, report **mean ± std**. Never a single lucky run.
- Same alert streams across policies (paired comparison) — this is a variance-reduction technique and a good thing to be able to explain.
- Fixed evaluation seeds, held out from training seeds.

## 12. Known limitations (write these in the report, do not hide them)

1. **The environment is simulated.** No real SOC telemetry. Every result is conditional on our generative assumptions.
2. **Severity being a weak predictor is an assumption we built in** (§4.2). It is defensible and industry-grounded, but it is the mechanism by which our agent can win.
3. **The DP "optimum" is optimal for an estimated model**, not the true environment.
4. **Our preference labels come mostly from students, not analysts.** We are learning *our* notion of good triage. Any practitioner labels we obtain should be reported separately.
5. **One analyst, one shift.** No multi-analyst coordination, no shift handover, no alert correlation into incidents.

Limitation 5 is also the obvious "future work" slide.
